# 项目协作与测试门槛（Project Rules）

> 文件路径：`docs/spec/steering/project-rules.md`
> 创建步骤：STEP 1（首次立规矩时生成）
> ⚠️ 本文件**不随 version 变更**，只在项目级做出调整时更新

---

## 沟通规范

1. 所有内容必须使用**中文**交流（包括代码注释与测试描述），用户界面文案与错误提示使用**英文**。
2. 遇到不清楚、歧义、缺失的内容应立即向用户提问，不得自行假设。
3. 表达清晰、简洁、技术准确。
4. 在代码中应添加必要的注释解释关键逻辑。
5. 当前任务完成后，提出下一步执行建议。

### 代码语言规范速查

| 内容 | 语言 | 示例 |
|------|------|------|
| 代码注释 | 中文 | `// 采集指定 pane 的终端 ANSI 输出内容` |
| 测试描述（`test()` / `TestXxx`） | 中文 | `TestCollector_CapturePane_Success` / `test('渲染 pane 卡片状态', ...)` |
| 函数名 / 变量名 | 英文（代码惯例） | `capturePaneOutput()` |
| 错误消息字符串 | 英文 | `'Pane not found'` |
| UI 文案字符串 | 英文 | `'Waiting for Input'` |
| Git commit message | 英文或中文均可，格式如 `TASK-XXX: <说明>` | — |

## Git 协作规范

### 主分支

- 主分支：`main`
- 跨平台换行符规范：根目录必须维护 `.gitattributes`，统一文本文件为 `LF`（Windows 批处理脚本保留 `CRLF`）。

### 任务分支

- 每个 TASK 独立一条分支：`feat/TASK-XXX` 或 `feat/TASK-XXX-short-slug`
- 验收通过后再合并到主分支；冲突时先报告用户，严禁 `--force`

### Commit

- 单次 commit 对应一个原子改动（一个 TASK 的一次提交）
- commit message 格式：`TASK-XXX: <简要说明>`

## 测试门槛与 QA 规范

- 每个 TASK 必须在合并前通过相关层级的测试：
  - Go 后端：`go test -v ./...` 全部通过，零编译错误，代码覆盖率符合基线
  - React 前端：`pnpm exec tsc --noEmit` 零 error，`pnpm test --run` 100% 通过
  - UI 变更：涉及 UI 变更时，必须使用 Playwright MCP 截图留证（Baseline 与 Diff）
- **禁止伪造测试结果**：严禁在未执行真实调用、未获取实际返回值的情况下输出 `PASS`。无法执行的用例必须标记 `BLOCKED` 并说明原因。
- **测试数据来源**：测试账号与测试数据统一从 `docs/spec/info.md` 获取，禁止自行捏造。

### TDD 铁律

```
⛔ 没有失败的测试，禁止写任何生产代码
```

顺序：红（编写失败测试并验证其报错）→ 绿（编写最小实现使测试通过）→ 重构（保持测试通过并优化结构）。

## 包管理与构建工具

- 前端：统一使用 **pnpm**。锁定文件 `pnpm-lock.yaml` 必须提交。禁止混用 npm 或 yarn。
- 后端：统一使用 **Go Modules**（`go.mod`, `go.sum`），依赖版本锁死，禁止使用不稳定 beta 版本。

---

## 环境变量与配置集中管理

- 所有常量和配置项统一管理在 `config/` 目录（例如 `config/agents.yaml`）。
- 敏感配置与环境变量通过 `.env` 管理，严禁在代码中硬编码任何密钥或端口信息。
- `.env` 必须加入 `.gitignore`。

---

## 开发工程化规范

1. **严禁重复**：任何重复逻辑必须抽象为可复用单元（函数、结构体、组件等）。
2. **检查现有代码**：先分析项目中是否已有类似实现。
3. **模块化设计**：将功能拆分为独立、高内聚、低耦合的可复用模块。
4. **统一接口**：使用一致的参数格式和返回值结构（标准 JSON 响应结构）。
5. **优先封装**：将相关功能和数据封装在独立的、职责明确的模块中。
